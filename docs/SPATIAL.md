# Spatial Audio Prototype（ブランチ: feature/spatial-audio）

普通のステレオ音源を、映画館やライブ会場のような広い空間で鳴っているように加工するプロトタイプ。
単純な左右パン・回転（8D 系）は目標外。重低音エンジン（Phase 00〜02.5）はそのまま残し、直列に接続している。

## 信号経路

```
source → 重低音グラフ（既定 OFF）→ 空間グラフ → モニター音量 → 出力
                                  │
空間グラフ: input ─┬─ BYPASS（原音）────────────────────────────────────────────┬─ output
                  └─ ステレオ化 ─┬─ [WIDE | CINEMA | HALL] → wet ┐                 │
                                 └─ HRTF 遅延補正 → dry ─────────┴→ トリム → リミッター ┘
```

- ORIGINAL / PROCESSED（B キー）は重低音・空間の両段を同時に BYPASS する。BYPASS 経路はゲイン 1 のみで、2 段直列でも原音とサンプル一致（自己診断で確認）
- トリム: 原音とラウドネス（BS.1770）をそろえ、「大きい方が良く聞こえる」錯覚なしで比較できるようにする（-12〜+6 dB、持ち上げはリミッター GR 3 dB 以内）
- リミッター: 重低音エンジンの AudioWorklet（サンプルピーク、-1 dBFS、先読み 5 ms）を低域入力なしで流用

## 3 モード

| モード | 処理内容 | INTENSITY | ROOM SIZE | DEPTH |
| --- | --- | --- | --- | --- |
| WIDE | Mid/Side。Side にだけ 500 Hz ハイシェルフ。Mid 高域（700 Hz〜）の遅延 2 タップを逆相で Side に注入（擬似アンビエンス、モノラル和で消える） | Side ゲイン 0〜上限（上限は原音の幅から自動、最大 +9 dB。S/M 比 -4.5 dB まで） | アンビエンス遅延 7〜37 ms | アンビエンス量 0〜0.3 |
| CINEMA | HRTF（PannerNode）で L/R を前方 ±20〜45° の仮想スピーカーに配置。床・天井・近い側壁・遠い側壁・後壁の初期反射 5 本/スピーカーをそれぞれの方向の HRTF に配置。HRTF の音色補正 EQ（低域 -3 / 1.25 kHz +4.5 / 6.5 kHz〜 +6 dB） | 開き角と反射量 | 反射遅延 ×0.6〜1.6 | 距離 1.5〜6 m（直接音レベル・空気吸収・反射の時間差） |
| HALL | 直接音 / 初期反射（左右 8 タップ、9〜64 ms×部屋）/ 後期残響（合成 IR 畳み込み、高域ほど早く減衰、プリディレイ）を分離。残響送りは 180 Hz〜9 kHz | 初期反射・残響の量 | RT60 0.9〜3.2 秒・反射間隔・プリディレイ | 直接音 0〜-9 dB・高域減衰・プリディレイ短縮 |

WET / DRY は全モード共通（処理音と原音の比率。原音側は HRTF 遅延 6.35 ms を補正して混ぜる）。

## 既知の制限

- **HRTF の個人差**: CINEMA の HRTF はブラウザ内蔵の汎用データ。前方定位が成立せず頭の中・後方に聞こえる人がいる。ヘッドホン専用（スピーカー再生ではクロストークで成立しない）
- **CINEMA の音色**: Chrome/Edge の HRTF は 200 Hz 付近 +4 dB、1.25 kHz 付近 -6 dB、8 kHz 付近 -10 dB の癖があり、補正 EQ 後も両耳の音色偏差は約 6 dB 残る
- **CINEMA のモノラル互換性**: バイノーラル信号をモノラルに混ぜると両耳間時間差でくし形の欠けが出る（音色偏差 約 6 dB）
- **WET/DRY の中間値**: CINEMA では遅延は補正しているが HRTF の位相差でコムフィルターが出やすい
- **WIDE の効果は音源依存**: もともと広い音源は上限によりほとんど広がらない。モノラル音源は Side ゲインが効かず、擬似アンビエンスだけが広がりを作る
- **HALL の残響**は合成 IR（実在ホールの測定データではない）
- **測定の待ち時間**: 読み込み時・パラメーター変更時に抜粋（最大 15 秒）をオフライン処理するため、CINEMA/HALL で 2〜6 秒程度かかる。その間も音は即時に反映される（トリムのみ測定後に更新）
- **重低音エンジンとの併用時**: 空間側のラウドネス合わせは原音（重低音処理前）を基準に計測している
- 検証は合成信号のみ。実楽曲での試聴による評価は未実施
- 5.1ch アップミックス、AI 音源分離は対象外（未実装）

# Phase 03: Dynamic Spatial Motion Engine

固定された空間から「音が独立して動く空間」へ。CINEMA / HALL で MOTION を ON にすると有効。OFF で既存の空間処理に戻る。

## 信号経路

```
root ─┬─ [CINEMA | HALL チェーン]  ← Motion ON 時: 直接音を止め、入力を「遅延をそろえた原音」に切替（反射・残響だけ使う）
      │
      └─ [csx-motion AudioWorklet]
            STFT 2048 / ホップ 1024（√Hann、50% オーバーラップ、遅延 42.7 ms @48kHz）
            帯域ごとのマスク → CENTER / LEFT / RIGHT / AMB L / AMB R / BED L / BED R（和 = 原音）
            各レイヤー: 伝搬遅延 → 空気吸収ローパス → 逆距離ゲイン → 等パワーパン
         ├ 出力0 12ch → 12 方向（30° 間隔）の固定 HRTF PannerNode → 音色補正 EQ → wet
         └ 出力1 遅延をそろえた原音 L/R → CINEMA の反射音 / HALL の初期反射・残響（HALL は HRTF 遅延分さらに遅延）
```

- HRTF は動かさない（固定 12 方向）。移動は振幅パンだけで表現するため、HRTF 切替ノイズ・PannerNode の大量生成がない（HRTF ノードは常に 12 個）
- 位置は `motion.ts` の純粋関数（メディア時刻・パラメーター → 位置）。乱数・壁時計なし。ワークレットには再生位置の基準（transport）を送るだけで、シーク・一時停止・再開・オフラインで同じ動きを再現
- 平滑化: 位置は単位ベクトルと距離を時定数 0.15 秒で平滑化（16 サンプルごと）、ゲイン類は制御点間を線形補間。シーク・再生開始時は平滑化せず正確な位置へ
- PULSE の包絡は曲全体から事前計算（10 ms ごと、アタック 80 ms、リリースは SPEED で 0.15〜0.8 秒）→ どこから再生しても同じ
- Motion OFF 時、ワークレットはフェード後 0.5 秒で処理を止める。使っていないモードのチェーンは入力を切り離す（CPU 対策）

## レイヤー分解

帯域ごとに L/R の自己・相互パワー（時定数 0.12 秒）から:
- 左右のレベルの釣り合い `bal = 2·min(σL,σR)/(σL+σR)`（片側だけ = 0）
- コヒーレンス（独立信号でも 0 にならない推定の偏り 1/√Neff を補正）と位相のそろい
- AMBIENCE = (1 − コヒーレンス)·bal、CENTER = CENTER LOCK·bal·同相度 × (L+R)/2、LEFT/RIGHT = 残り
- 120〜200 Hz 以下は BED（固定）へ滑らかに振り分け

通常のステレオ音源から楽器は分離できない。レイヤーは統計的な分類で、同じ楽器が複数のレイヤーにまたがる。

## プリセット（t = 再生位置、T = 周期 40〜5 秒、m = MOTION DEPTH）

| プリセット | LEFT / RIGHT | AMBIENCE | 距離 |
| --- | --- | --- | --- |
| CINEMATIC | 基準角の外側で、位相の異なる 2 つの正弦波のゆらぎ（最大 ±22°·m） | 側方〜後方で ±35°·m | ±35%·m |
| ORBIT | それぞれの側で前方〜後方へ（±(40+50m)°） | 180° 離れて聴取者の周囲を一周 | わずかに変化 |
| SWEEP | 左右を横断（±(40+50m)°、90° 位相差） | 固定 | 固定 |
| PULSE | 包絡が大きいほど広く（+55°·m）・近く | 同様に広がる | 小さいほど遠い（最大 +80%·m） |

## 既知の制限（Motion）

- STFT 分解の遅延 42.7 ms。ORIGINAL/PROCESSED 切替でこの分だけ時間がずれる

- Motion ON の直接音は HALL でも HRTF 描画 → ヘッドホン前提。HRTF の個人差により前後・定位が成立しない人がいる
- CINEMA の音色偏差（モノラル和）約 7 dB、HALL のモノラル和ラウドネス -1.3〜-1.6 LU
- CPU 負荷（未使用チェーンの切り離し後に再計測: CINEMA×ORBIT 13.3% / HALL×ORBIT 20.5% / 全チェーン構築 22.2%、オフライン換算）
- SPEED/プリセット変更時は 0.15 秒の平滑化で新しい軌道へ移る（速い移動に聞こえる場合がある）

## 信号経路（Tail）

```
送り（Motion OFF: 原音〈CINEMA は HRTF 遅延分遅らせる〉／ Motion ON: Motion の遅延をそろえた原音）
  ─┬─ HPF 180 Hz → LPF 9 kHz → モノラル → プリディレイ → [ReverbBus: ConvolverNode（モード別の合成 IR）] → レベル ─→ [csx-tail] → wet
   └────────────────────────────────────────────────────────────────────────────────────────── 検出器 ──┘
```

- HALL では既存の後期残響（同じ構成）と入れ替える。初期反射はそのまま。CINEMA では反射音に後期残響を加える。WIDE では使えない
- NATURAL の TAIL LENGTH / INTENSITY 50 は HALL と同じ値（RT60・プリディレイ・レベル）。Dynamic OFF かつ蓄積防止が働かなければ csx-tail のゲインは厳密に 1
- 余韻の方向・広がり・周波数ごとの消え方は IR に書き込む（線形時不変）。曲の途中の音にも停止後にも同じ性質が現れ、OfflineAudioContext でも同じになる（Phase 06 の書き出しは、音源の長さ + 余韻の長さをレンダリングすれば余韻を含められる）

## Dynamic Tail（csx-tail ワークレット）

- 検出: 短時間レベル（アタック 5 ms / リリース 30 ms）と、曲の平均レベル（100 ms 平均パワーを上昇 0.4 秒・下降 2 秒で追従、−70 dBFS 未満では更新しない）
- 演奏の密度 a = 短時間レベルが平均より 15 dB 低いと 0、そこから 12 dB の幅で 1。目標 = −8 dB × a
- 下げる側は速く（Attack 25 ms）、戻す側は Hold 150 ms の後に Release 250 ms、最後に 10 ms の平滑化。設定レベル（0 dB）より大きくしない
- 残響の「戻り」に掛ける（送りではない）: 演奏中に下げた残響が、切れ目で設定レベルへ戻って広がる
- 蓄積防止: 戻りが平均レベル − 3 dB を超えたら抑える（アタック 0.2 秒・リリース 1 秒）。平均レベルが定まる（音が鳴って 0.5 秒）までは働かない。停止後は残響が減衰した分だけ抑制を外す（余韻が持ち上がらない）

測定: 0.6 秒の音 → 1.4 秒の切れ目で、音の途中 −8.0 dB、立ち上がり 60 ms 後 −6.6 dB、切れ目 100 ms 後 −8.0 dB（Hold）、0.45 秒後 −2.6 dB、0.9〜1.2 秒後 −0.3 dB。定常ノイズで揺れ 0.00 dB、80 ms の隙間のリズムで変動 0.0 dB、1 サンプルあたりの変化 3.4e-4。

## Motion と残響の統合

- 方式 B（Spatially Responsive Reflections）: Motion ワークレットの出力 1（反射音・残響への送り）を「原音の遅延」から「LEFT/RIGHT レイヤーを現在の左右位置に振り分けた全レイヤーの和」に変更。動きが 0 なら原音と一致（全レイヤーの和 = 原音）。距離処理は掛けない（距離で直接音/残響比が変わる性質は維持）
- 方式 C（Stable Late Reverberation）: 後期残響（HALL・Tail）はモノラル送りのまま → 位置によらず安定
- CENTER・AMBIENCE・BED の送りは元のチャンネルのまま（AMBIENCE を追従させると PULSE で後方へ回り込むときに反射だけが狭まり、PULSE の広がりの相関が 0.84 → 0.57 に下がったため）
- 反射音を減らす方式（D）は使っていない（初期反射・後期残響のレベルは Phase 03 と同じ）
- 結果: 既定値（反射あり）の SWEEP の ILD 変化幅 約 11 dB → LEFT 16.1 dB / RIGHT 17.6 dB（追従相関 0.95 / 0.97）。ORBIT の ILD 変化幅 16.6 / 20.7 dB。PULSE の広がりの相関 0.89

## 停止系とループ

| 操作 | 処理 | 測定 |
| --- | --- | --- |
| STOP | 音源のゲインを 12 ms でフェードして止める（グラフはそのまま） | 余韻の長さは従来の停止と同じ（HALL 1680 ms）、440 Hz の 2 階差分比 1.00（フェードなしの途切れは 17.35）。実アプリ: −33 dB → 100 ms 後 −50 dB → 1 秒後 −76 dB → 1.5 秒後 −90 dB |
| PAUSE | 出力ゲートを 20 ms で 0 → 後期残響を消す（入力から各畳み込みまでの遅延を足した時刻で切替）→ 再開は遅延線が空になる 0.25 秒後以降 | 20 ms 後から完全に無音、再開後は新規再生との差 −72.9 dB、Motion の位置の差 ≤ 0.51 dB |
| CUT | PAUSE と同じ方法で止めて先頭へ（STOP 後に鳴っている余韻も止める） | 20 ms 後から完全に無音 |
| SEEK（再生中） | 新旧の音源を 10 ms でクロスフェード（余韻は残す） | — |
| NORMAL LOOP | ネイティブループ（ファイル全体）。境界で後期残響を消す（入力を 10 ms で別の畳み込みへ受け渡し、古い方を 80 ms でフェード） | 3 周目以降が 2 周目と一致（−76 dB、実測の下限 −76 dB）、前回の残響の残り −40.9 dB、境界の 2 階差分比 1.00 |
| SPATIAL LOOP | 音楽の区間（−60 dBFS を超える最初〜最後のサンプル、前 5 ms・後 20 ms の余裕）をループ。残響は消さない | 次の冒頭に前回の余韻が重なる（差 −15.0 dB）、4 周目以降は毎回同じ、3〜8 周目のラウドネス幅 0.0 LU |

- メディア時刻は `transportTime()`（ループ区間で折り返す）で再生位置・Motion・可視化が共通。Motion の位置はループ境界で 0.15 秒の平滑化で新しい位置へ移る
- 畳み込みは最大 3 組を使い回す（入力を閉じてから IR の長さ以上たった組は内部状態がすべて 0）。境界のたびに作ると、実時間で 1 回あたり十数 MB のメモリが GC されるまで積み上がった（22 秒で +192 MB を測定 → 使い回し後は約 50 秒で +2〜+27 MB）
- NORMAL LOOP の境界の消去は、境界の 0.4 秒前にタイマーで AudioParam を予約する。タブが背面でタイマーが遅れると、消去が境界より遅れることがある

## 試験方法の変更（Phase 04 で書いた試験の基準を、実測で分かったブラウザの性質に合わせたもの）

- 周回の一致: 当初「差 ≤ −80 dB」→「同じグラフに入力を 1 周期ずらして入れたときの差（実測の下限）+ 3 dB」。Chrome の DelayNode は小数サンプルの遅延で時不変でなく（単体で入力をずらすと −56 dB の差）、HALL の初期反射を含むグラフでは −76 dB 前後より小さくならないため
- NORMAL LOOP: 当初「2 周目以降が 1 周目と一致」→「3 周目以降が 2 周目と一致」＋「1 周目との差のエネルギー比 ≤ −30 dB（前回の残響が残らない）」。境界のクリックを防ぐため入力を 10 ms で受け渡すようにした結果、境界付近 10 ms の音の残響が新旧に分かれ、無音から始まる 1 周目とは原理的に一致しないため
- メモリ: 当初「オフラインのループ後の JS ヒープ増加 ≤ 50 MB」→「実時間の再生エンジンで 50 秒ループ再生したときのブラウザ全体の物理メモリ増加 ≤ 50 MB」（実行スクリプトが OS から測定）。Chrome は AudioWorklet を読み込んだ OfflineAudioContext を解放せず、JS ヒープの値も実際のメモリと連動しないため、オフラインではループ処理自体のメモリを測れない

## 既知の制限（Phase 04）

- **Chrome は AudioWorklet を読み込んだ OfflineAudioContext を解放しない**（ノードを作らず addModule だけでも同じ。レンダリング結果の分だけメモリが残る）。アプリでは設定変更のたびの解析（音量合わせ・指標）で 1 回あたり数 MB〜10 MB が残る（Phase 02 以降の既存の解析も同じ）。解析を 250 ms 間引いて回数を減らしたが、根本的には解消していない

- DISTANCE・RIPPLE は合成 IR による演出（実在の空間の測定ではない）。HRTF の方向情報は使っていない（ヘッドホン・スピーカーとも同じ IR）
- Dynamic Tail は音量だけで「切れ目」を判定する。密なミックスでは常に −8 dB 側にあり、効果は「余韻が控えめになる」方向に出る
- TAIL LENGTH の変更時は IR を再生成してクロスフェードする（8 秒の IR の生成・畳み込みカーネルの計算に数十 ms）
- 実楽曲・ヘッドホンでの試聴による評価は未実施

## 信号経路（プリセット適用時）

```
音源 ─→ [重低音: EQ → LR4 150 Hz → 低域コンプ → 合成 → トリム → リミッター（先読み 5 ms）]
     ─→ [空間: ステレオ化 ─┬─ CINEMA / HALL のチェーン（反射音・Tail）─┐
                          ├─ Motion（STFT レイヤー分解 → 12 方向 HRTF）─┤→ トリム → リミッター（先読み 5 ms）]
                          └─ 遅延補正 → dry ─────────────────────────┘
     ─→ 出力ゲート（PAUSE / CUT）→ モニター音量 → 出力

ORIGINAL: 音源 ─→ [重低音の BYPASS: 時刻合わせ 5 ms] ─→ [空間の BYPASS: 時刻合わせ（処理経路の遅延）] ─→ …
```

## ORIGINAL / PROCESSED 比較

- 1 つの音源を、各段の BYPASS 経路と処理経路のクロスフェード（40 ms）で切り替える（二重再生・再生位置の移動なし）。
- **時刻合わせ**（`alignDelay.ts` / `align.worklet.ts`）: ORIGINAL 経路を処理経路で中央の音が出てくるまでの遅延だけ遅らせる
  = モードの遅延（Motion の STFT 2048 サンプル + HRTF）+ 出力段リミッターの先読み 5 ms + Motion の CENTER の伝搬遅延（基準距離の分）+ 重低音段の先読み 5 ms。
  整数サンプルのワークレットなので、遅延した原音とビット一致する（DelayNode は float32 の秒で小数サンプルが残り補間されるため使わない）。
  遅延の変更は ORIGINAL 経路が無音のとき（PROCESSED 再生中）だけ AudioParam で予約する。ORIGINAL を聴きながら設定を変えた場合は、PROCESSED に戻すときに遅延の差だけずれる。
- **ラウドネス**: 空間段の最後のトリムで、重低音段を含むチェーン全体を原音のラウドネスにそろえる（重低音 ON のときは重低音段を通した音で解析する）。持ち上げはリミッターの GR 予算 3 dB 以内で、ピーク制限は変えない。

## CUSTOM と保存

- カードから適用した後に詳細設定を変えると CUSTOM（元のカードは点線で「CUSTOM」表示）。プリセットの元データは凍結されていて変わらない（同じ値に戻すと元のプリセットに一致）。
- 「現在の設定を CUSTOM として保存」で localStorage に保存（DSP 設定の数値と元のプリセットの ID・版・保存日時のみ。音声・ファイル名は保存しない）。
  読み込み時は型・範囲を検証し、壊れた・古い形式のデータは読み込まずにメッセージを出す。保存に失敗しても例外を投げず、再生は続く。

## 解析処理の最適化（メモリ）

Chrome は AudioWorklet を読み込んだ OfflineAudioContext を解放しない（Phase 04 で確認）。設定変更のたびの解析（ラウドネス合わせ・指標）が文脈を残すため、次のように減らした。

| 対策 | 内容 |
| --- | --- |
| 実行条件 | 重低音 OFF の間は重低音の計画を立てない（ON にしたとき計画。状態表示「重低音 OFF（ON にすると計測）」）。空間 OFF は解析しない |
| キャッシュ | 同じ音源・同じ設定の計画を 24 件まで保持（LRU、音源が変わると消す）。キーは音に効く項目だけ（WIDE の Motion 設定・Tail OFF の LENGTH などは含めない）。重低音 ON のときは空間のキーに重低音の設定を含める |
| 重複の防止 | 直近に適用した計画と同じ設定なら解析しない。解析待ちの間に計画済みの設定へ戻した場合も解析しない |
| 頻度 | 250 ms のデバウンス（Phase 04 から）。キャッシュにある設定は待たずに即座に反映 |

## 既知 FAIL（Phase 04 の HALL × SWEEP × RIPPLE + DYNAMIC、−1.3 LU）の原因

`?suite=preset&groups=51-51`（ステレオミックス 8 秒、空間段のみ）で、組み合わせを 1 つずつ変えて「トリム前のラウドネス・ブロックピーク（99.9%）・ピーク対ラウドネス比（PLR）・必要なトリム・予算内の上限」を測った（Chrome）。

| 条件 | トリム前 | PLR | 必要なトリム / 上限 | 結果 |
| --- | --- | --- | --- | --- |
| 原音 | — | 8.3 dB | — | — |
| HALL × SWEEP × RIPPLE + DYNAMIC（FAIL） | −3.3 LU | 12.2 dB | +3.3 / +2.4 dB | −1.4 LU |
| DYNAMIC TAIL なし | −2.8 LU | 12.1 dB | +2.8 / +2.1 dB | −1.2 LU |
| Tail OFF（既存 HALL の残響） | −5.6 LU | 12.6 dB | +5.6 / +4.4 dB | −1.8 LU |
| NATURAL + DYNAMIC | −3.3 LU | 12.4 dB | +3.3 / +2.2 dB | −1.5 LU |
| SWEEP → CINEMATIC | −3.6 LU | 12.6 dB | +3.6 / +2.3 dB | −1.7 LU |
| Motion OFF | −2.4 LU | 9.8 dB | +2.4 / +3.9 dB | −0.2 LU |

**原因は HALL + Motion で PLR が原音より約 4 dB 上がること**（Motion OFF の HALL は +1.5 dB）。トリムで持ち上げるとピークが先にリミッターの予算（GR 3 dB）に達し、原音のラウドネスまで上げられない。
Dynamic Tail・RIPPLE・SWEEP の影響は小さい（各 ±0.3 LU 程度）。Phase 04 のドキュメントでは「Dynamic Tail が残響を下げ続けるため」としていたが、測定により主因ではないと分かったので訂正する。
対策: 試験基準は変えず、ピーク制限も破らない。標準プリセットでは HALL + Motion を使わない（IMMERSIVE X を CINEMA + Motion に変更）。test:tail の該当項目は FAIL のまま残す。

## Phase 05 で見つけて修正した既存の不具合

- **Motion ON・Tail OFF の解析が反射音を含んでいなかった**（Phase 03 から）: 解析グラフを Motion のチェーンだけで作っていたため、CINEMA / HALL の反射音（CINEMA ではエネルギーの大半）を除いた音でラウドネス合わせのトリムを決めていた。トリムが過大（例: CINEMA × CINEMATIC で +5.1 dB）になり、実際の出力ではリミッターが設計上の予算（GR 3 dB）を超えて働いて原音のラウドネスに見えていた。モードのチェーンを常に含めるよう修正（同じ条件のトリムは +3.1 dB）
- **Motion ON の CINEMA で初期反射が直接音より先に届いていた**（Phase 03 から）: Motion の直接音は距離に応じて遅れる（3.5 m で 7.4 ms）が、反射音への送りは遅れないため、2〜19 ms の反射音が直接音より前に来ていた。CINEMA の反射音への送りを CENTER の基準距離の伝搬遅延だけ遅らせた。HALL の初期反射（9 ms × 部屋の倍率〜）・後期残響の送りは変えていない
- **CINEMA の INTENSITY 変更でクリック**（プロトタイプから）: HRTF の PannerNode の位置を連続的に動かしていた（2 階差分比 2.95）。固定方向の 2 つのパンナーのクロスフェードに変更（1.00）
- **IR の切替（Tail の種類・LENGTH、HALL の ROOM SIZE）で小さなクリック**: 新しい畳み込みの入力を瞬時に入れていた（1.45〜1.54）。入力も 10 ms で立ち上げる（1.00〜1.11）
- **遅延時間の変更でクリック**: DelayNode の delayTime を自動化すると、固定から自動化に変わる瞬間に出力が飛ぶ（Chrome。DEPTH 55 → 30 で 3.34）。新しく追加した送りの遅延は固定の遅延 2 つのクロスフェードにした（1.01）

# Phase 06: Audio Export Engine（オフラインレンダリング・WAV 書き出し）

音源を読み込み、プリセット（または詳細設定）を選び、EXPORT で加工済みの音声（音源 + 余韻）を WAV として生成・試聴・ダウンロードする。
再生と書き出しで別の DSP を持たない: 書き出しは `createOutputChain`（重低音 → 空間）と、再生中のグラフと同じ処理計画（`AudioEngine.exportSnapshot()`: 重低音の EQ 倍率・ダイナミクス、空間のトリム・WIDE の Side 上限）を使う。

## 書き出しの流れ

```
EXPORT
 ├ PREPARING: 処理計画の取得（解析が終わっていなければ待つ）→ 元のサンプルレートでデコードし直す（AudioContext のレートと違う場合）
 │            → メモリの見積もり（上限を超えたら書き出し前に止める）→ 解析を止める・再生を一時停止して AudioContext を止める
 │            → 使い捨ての iframe（export-frame.html）を作り、音源の PCM を転送
 ├ RENDERING: iframe の中で OfflineAudioContext（2ch・元のレート・長さ = 処理の遅延 + 音源 + 余韻 + 0.25 秒）に
 │            createOutputChain を作り、音源を時刻 0 から再生（Motion の transport も時刻 0 から = 曲の先頭からの動き）。
 │            進捗は OfflineAudioContext.suspend を 40 回入れて、実際に描画し終えた時刻の割合を通知（推定値ではない）
 ├ ENCODING:  先頭の処理の遅延を切り捨て、末尾を切り詰め・フェードし、WAV（16-bit TPDF ディザ / 24-bit）に変換
 └ COMPLETE:  Blob を親へ返し、iframe を削除 → Object URL を作り、完了表示・ダウンロード・プレビュー
キャンセル: iframe を削除（OfflineAudioContext には途中で止める API がない）→ 結果を作らない
```

## 余韻の書き出し

- 長さは設定から計算する（`reverbTailSeconds`）: 後期残響（HALL の後期残響 / Spatial Tail）の IR の長さ（RT60 × 1.3、上限 4.5 / 8 秒）+ プリディレイ、反射音の最大遅延。固定値ではない。上限は IR の長さで決まる（最長 約 8.6 秒）
- レンダリング後、最後に −100 dBFS（16-bit の 1 LSB より小さい）を超えたサンプルから 150 ms 後で切り、最後の 20 ms をフェード（余韻の本体は切らない。最後のサンプルは 0）
- 既存 HALL（既定値）の停止後の余韻（−60 dB まで）: 書き出しで 1650 ms（Phase 04 のベースライン 1680 ms と同じ測り方、±40 ms 以内）

## 先頭の時刻合わせ

処理の遅延（重低音の先読み 5 ms + Motion の STFT 2048 サンプル + HRTF + 出力段の先読み 5 ms）を先頭で切り捨て、書き出した音を元の音源と同じ時刻にそろえる（最も早く出てくる音に合わせるので、何も失わない）。
Motion の CENTER は距離に応じた伝搬遅延（4.4 m で 10 ms）だけ後ろに来る（意図した遅れ）。

## Phase 06 で見つけて直したこと

- **HRTF の同時処理で書き出しの結果が変わる（Chrome）**: 再生側の AudioContext が HRTF を処理している（停止中も Motion・CINEMA のチェーンは処理を続ける）と、OfflineAudioContext の HRTF PannerNode の結果が回ごとに変わる（同じ設定で −2.7〜+1.6 dB の差。PannerNode 単体でも再現。再生側を止めている間は毎回一致）。
  書き出しの前に再生側の AudioContext を止める（`suspendForExport`）ようにした（書き出しの後に再開）。
  再生していない状態が続いたら自動で止める方式も試したが、止めている間はブラウザが切り離したノード（畳み込み）を解放しないため、停止中にプリセットを切り替えるたびにメモリが積み上がった（20 回で +670 MB）。そのため書き出し中だけ止める
- **重低音 OFF のとき、音源の終わりで最後の 5 ms が欠ける**（Phase 05 の時刻合わせのワークレット）: 入力が切れると出力のチャンネル数が変わり、遅延線に残った音（右チャンネル）を出さずに終わっていた。出力を常に 2ch に固定
- **STOP・自然終了で、処理中に残っている音（約 55 ms）の Motion の位置が先頭の位置へ飛ぶ**: Motion の時刻を止めるのを 250 ms 遅らせた（書き出しとの末尾の差 −14 dB → −51 dB）

## 既知の制限（Phase 06）

- **サンプル単位では一致しない**（上記。統計的な指標は一致）。書き出しを基準にするなら、書き出した WAV のプレビューで確認する
- **書き出し中は再生できない**（再生側の AudioContext を止めるため。終わると再開し、再生ボタンで続きから）
- **解析と HRTF の同時処理**: 解析用の OfflineAudioContext も HRTF を使うため、再生側の AudioContext が動いている間（停止中も動いている）の解析は、結果（ラウドネス合わせのトリム）がわずかに変わる可能性がある（Chrome の HRTF の同時処理の問題。書き出しは止めてから行うので影響しない）。影響の大きさ・再生側の音への影響は測っていない
- **長い音源**: 3 分のステレオ（IMMERSIVE X）でレンダリング 約 110 秒（実時間比 約 60%、このテスト環境）。分割レンダリングは Motion の STFT・残響・Dynamic Tail の状態が分割点で不連続になるため採用していない。30 分・メモリの見積もりの上限を超える音源は書き出せない（エラー表示）
- **書き出しのメモリ**: 使い捨ての iframe で行うため、書き出しの後にメモリは戻る（60 秒 × 3 回で増加なし。iframe を使わないと 1 回 +110 MB 残る）。ただし書き出しの最中は見積もり（3 分で 約 460 MB）程度を使う
- **実時間の記録での途切れ**: 試験の実時間の記録で、1 回だけ 4.9 秒付近に途切れ（その区間の差 −9.8 dB）が記録された（ヘッドレスの Chrome・他のアプリが動作中。統計的な指標は合格）。実際の再生の途切れか記録側の遅れかは区別できていない
- MP3・FLAC・Ogg・M4A の実ファイルでの書き出しは未検証。実楽曲・ヘッドホンでの試聴は未実施

## 処理の流れ

```
読み込み: 拡張子が mp4 / m4v / mov / webm / mkv → 中身を判定（mediabunny、ファイル全体は読まない）
  ├ 映像トラックあり → 動画: コンテナ・コーデック・解像度・フレームレート・音声トラックを表示
  │                   主な音声トラックを WebCodecs でデコード（各サンプルのタイムスタンプの位置に並べ、元のサンプルレートのまま）
  │                   → 再生エンジン（立体音響の試聴）・書き出しで使う
  └ 映像トラックなし → 従来の音声ファイルの経路（decodeAudioData）
書き出し:
  1. ORIGINAL AUDIO: 抽出した音声をそのまま WAV
  2. SPATIAL AUDIO : Phase 06 の書き出し（余韻を最後まで含む WAV）
  3. 動画           : Phase 06 の書き出し（使い捨て iframe、WAV は作らず浮動小数点で受け取る）
                     → mediabunny で出力を組み立てる: 映像の符号化済みパケットをコピー（タイムスタンプ・キーフレームそのまま）
                       + 加工済みの音声を AAC（MP4 / MOV）/ Opus（WebM / MKV）でエンコード（元の音声トラックの開始時刻から）
```

## 同期の設計

- 映像: パケットのタイムスタンプ・長さをそのままコピーする（再エンコードしない）
- 音声: 元の音声トラックの最初のタイムスタンプ（開始 PTS）から並べる。decodeAudioData はこの開始時刻を失う（実測: 0.5 秒後に始まる音声の 1.0 秒のクリックが 0.5 秒に来る）ため、抽出には使わない

## Phase 07 の安定化（2026-10-20）: Edge で書き出しが止まる問題・書き出しの後のメモリ

### 1. Edge で書き出しが止まる問題

**症状**: Edge で、書き出し（使い捨ての iframe。Phase 06 の経路で、動画の書き出しも使う）がまれに準備の段階（PREPARING）から進まず、終わらない。止まった間は OfflineAudioContext が running のまま、CPU は使われない。安定化の前の Edge の test:export は 60〜62 が 4 回とも・68 が 2 回とも止まり、test:video も 85・86〜87 が 1 回ずつ止まった。Chrome は 0 回。

**段階の記録で分かったこと**（フレーム・親の各段階の開始・完了・失敗を console.debug と記録に出すようにして測定。下記 3.）:
- 止まるのは毎回 **HRTF の遅延の測定（`measureHrtfLatency`: HRTF の PannerNode を通す 0.1 秒の OfflineAudioContext）の開始の直後**。例: 60〜62 では 1 回目（44.1 kHz）の書き出しは全段階が完了し、2 回目（48 kHz）の新しいフレームが `hrtf` の開始を記録した後に何も来ない。68 では最初の書き出しで止まる
- 止まり方は 2 通り: (a) メインスレッドは応答し、OfflineAudioContext が running のまま（Promise が解決しない）、(b) **メインスレッドごと止まる**（CDP の Runtime.evaluate が 5 秒応答しない）。(b) では、同じスレッドで動く親の監視のタイマーも動けない（書き出し用の iframe は同じオリジンなので親と同じスレッド）
- 書き出しの前の再生エンジンの準備（ページ内の `measureHrtfLatency`）でも同じ止まり方をする（試験用の動画の書き出しの前で止まり、新しい文脈で測り直しても止まったままだった）

**原因**: ブラウザ（Edge）内部の、HRTF のデータ（サンプルレートごとに作られ、使う文脈がなくなると破棄される）の作成・破棄に関係すると考えられるが、**確定していない**。アプリのコードを使わない最小の再現（HRTF の OfflineAudioContext をフレームごとに 44.1 / 48 kHz で交互に 20 回 × 3、AudioWorklet・畳み込み・進捗用の suspend → resume を加えたもの 600 回）では一度も止まらなかった。その後の追加の最小の再現（Edge・iframe・44.1 → 48 kHz）は 1 件目（ページ内）が完了した後、2 件目が結果を出さないまま終わらず、ブラウザのプロセスも残っていなかったため、止まったのか外から終了されたのか判定できない（結果なしとして扱う。2026-10-21 に停止）。

**対策の効果の比較**（Edge、交互に実行）:

| 試験 | HRTF のデータを保持（対策） | 保持しない（以前の動作） |
| --- | --- | --- |
| test:export 60〜62（44.1 → 48 kHz を含む 12 回の書き出し） | 6 / 6 完了 | 1 / 6 完了（5 回とも `hrtf` の開始で止まった） |
| test:video 86〜87（ページ内の HRTF の測定 → 動画の書き出し） | 15 / 15 完了 | 12 / 15 完了（3 回はページ内の測定が 2 回とも止まりエラー） |

### 2. 実装した対策

1. **HRTF のデータの保持**（`src/audio/hrtfKeeper.ts`）: 書き出す・測るサンプルレートごとに、ページに小さな OfflineAudioContext（128 フレーム・レンダリングしない・ワークレットなし）+ HRTF の PannerNode を 1 つ持ち続ける。書き出しの開始（exportRunner）と `measureHrtfLatency` の前に作る。上の比較で止まらなくなった（原因の確定ではない）
2. **HRTF の遅延の測定の上限と測り直し**: 1 回 10 秒で打ち切り、新しい文脈で 1 回だけやり直す。2 回とも終わらなければエラー（「ページを読み込み直してください」）。失敗した測定はキャッシュしない（以前は止まった Promise を覚えてしまい、以後の測定がすべて待ち続けた）
3. **書き出しの監視**（`exportRunner.ts`）と段階の記録（下記 3.）
4. **準備と音源の送信の分離**: フレームへの要求を 2 段階にした（prepare: 音源なしで HRTF の測定・文脈・ワークレットを準備 → prepared → render: 音源を転送）。準備で止まった場合は音源を送る前なので、音源のコピーを持たずに新しいフレームで作り直せる
5. **再生エンジンの準備も上限に含める**: `exportSnapshot` の 120 秒の上限に、エンジンの準備（`ensureReady`）を含めた
6. **動画の書き込みの監視**（`videoExport.ts`）

### 3. 監視（タイムアウト）の仕様

| 段階 | 判定 | 上限（既定） | 打ち切った後 |
| --- | --- | --- | --- |
| 準備（PREPARING: フレームの生成〜初期化〜HRTF の測定〜文脈〜ワークレット〜音源の受け渡し〜チェーンの構築〜startRendering） | 段階の記録が届かない時間 | 30 秒（通常の準備は 0.2〜0.4 秒） | 音源を送る前なら新しいフレームで **1 回だけ** 自動でやり直す。2 回目も止まれば ExportTimeoutError |
| レンダリング（RENDERING） | 進捗（実際に描画済みの割合）が届かない時間 | 60 秒 | ExportTimeoutError（音源は転送済みなので作り直さない） |
| エンコード（ENCODING: WAV への変換〜結果の受け取り） | 開始からの時間（同期処理で途中の進捗がない） | 60 秒 + 音声 1 秒あたり 0.2 秒 | ExportTimeoutError |
| 動画の書き込み（MUXING） | 映像のパケット・音声のまとまり（0.5 秒）の進捗が届かない時間 | 60 秒 | VideoTimeoutError |
| ページ内の HRTF の遅延の測定 | 1 回の時間 | 10 秒 × 2 回 | エラー（再生エンジンの準備の失敗） |

- 長い音源で誤って止めないよう、レンダリングの進捗は「全体の 1/40、ただし音声 5 秒ごと以下」の間隔で届くようにした（30 分の音源でも 5 秒ごと）。60 秒の IMMERSIVE X の書き出しで進捗の間隔の最大は 0.8 秒（上限の 1/75）
- 自動のやり直しは準備の段階・音源を送る前だけ、1 回まで（無限に繰り返さない）。出力は時刻の純粋関数なので、やり直しても結果は同じ
- 監視は親のタイマーで行う。**メインスレッドごと止まった場合（上の (b)）は、ページの JS では検出も復旧もできない**（タブ全体が応答しなくなる）。この場合は HRTF のデータの保持で発生を防ぐことだけが対策

### 4. 打ち切り・キャンセルの後始末（復旧）

- 書き出し用の iframe を削除（文書ごと文脈・ワークレット・バッファーを破棄）、メッセージの受信・監視のタイマーを解除
- 動画の書き込みは AbortSignal で中止し、書きかけの出力（mediabunny の Output）を cancel して破棄
- 結果（Blob・Object URL）を作らない（完了したときだけ作る）。UI（useAudioPlayer）は実行中の状態を解除し、再生側の AudioContext を再開し、エラーを表示する（「書き出しが途中で止まったため中止しました。もう一度書き出してください。」+ 止まった段階・秒数）。そのまま再び書き出せる
- Worker は使っていない（書き出しは iframe、動画の処理はメインスレッドの WebCodecs）ので、終了する Worker はない
- 試験（グループ 72・90）: 止めた状態は試験専用の `debugStall`（その段階の開始で戻らない Promise を待つ）と `debugMuxStallAfterPackets` で作る。準備・レンダリング・エンコード・動画の書き込みのそれぞれで打ち切り → iframe なし → その後の書き出し（WAV のヘッダー・長さ、動画のパケット数・同期）が正常なことを Chrome / Edge で確認

### 5. 段階の記録（ログ）

- 書き出しごとに処理 ID（`export-<n>`）・試行の回数・ブラウザ（`Edge 155` など）・入力条件（サンプルレート・チャンネル数・長さ・空間のモード・Motion・重低音・WAV / 浮動小数点）・11 の段階（frame / init / hrtf / context / worklets（モジュールごと）/ transfer / chain / render-start / render / encode / return）の開始・完了・失敗と経過時間（ms）を記録する（`recentExportTraces()`、直近 30 件）。打ち切ったときは console.warn にも出す
- フレームと親は各段階を console.debug にも出す（スレッドごと止まっても、止まる直前の段階まで DevTools に届く。試験のランナーは `--log` で表示する）
- **音声のサンプル値・ファイル名は含めない**（グループ 72 で確認。1 件 約 1.8 KB）

### 6. 書き出しの後に残るメモリ（グループ 88 の FAIL）

**条件の特定**:
- ページ内に AudioWorklet を読み込んだ OfflineAudioContext（再生エンジンの解析）があるときだけ起きる。再生エンジンがないと残らない（+1 MB）
- 残るのは **レンダリングの出力のバッファー 1 本分**（OfflineAudioContext の出力。3 分で 約 68 MB）。音源の配列を写した直後に手放しても、音源の AudioBuffer をノードから外しても、WAV の書き出し（フレーム内にさらに約 210 MB の浮動小数点・WAV がある）でも、残る量は 68 MB で変わらない（フレーム全体が残るのではない）
- JS から解放する方法はない（OfflineAudioContext には close がない）。ブラウザ内部のどのオブジェクトが参照を持つかは未確定

**解放までの時間**（書き出し 1 回の後、5 秒おきに gc() して JS ヒープを測定）: Chrome・Edge とも約 16〜21 秒（以前の測定では Edge 約 40 秒）。再生用の AudioContext を止めたままでも同じ。次の書き出しの間は戻らない。

**連続書き出しのピーク**（グループ 98、3 分の動画を 4 回続けて）: JS ヒープ 116 → 185 → 254 → 323 → 391 MB、レンダラーの private 737 → 766 → 832 → 910 → 983 MB（Chrome）。60 秒放置の後 117 MB / 663 MB に戻る。Edge はこの回は積み上がらなかった（JS ヒープ 116 → 185 → 185 → 117 → 186 MB。書き出しの合間に戻ることがある。残る時間は回によって変わる）。test:video 全体のブラウザのピーク（ワーキングセットの合計）Chrome 1341 MB / Edge 1363 MB。

**キャンセルの後**（グループ 98、3 分の動画のレンダリング中に 3 回キャンセル）: JS ヒープは増えない（118〜121 MB）が、レンダラーの private が 1 回ごとに約 +90〜190 MB 増え（Chrome 716 → 804 → 968 → 1154 MB）、60 秒放置の後 646 MB に戻る（書き出しと同じく一時的）。

**対策**:
- 書き出しの後の残りを見積もり（`pendingRetainedBytes`: 文脈を作った書き出し・キャンセル・打ち切りごとに出力 1 本分）、次の書き出しのメモリの見積もりに足して上限（`exportMemoryBudget`）を超える場合は書き出しを始めない（「約 N 秒待ってから、もう一度書き出してください」）。書き出しのない時間が 45 秒続いたら 0 と見なす（測定の最大 約 40 秒より長く）
- 書き出し用フレームで、音源の配列を AudioBuffer に写した直後に手放す（レンダリング中のピークを 3 分で 約 69 MB 下げる。残る量は変わらない）
- 安定化の途中で、動画の書き込みの中止用のリスナーが同じ関数の音声の配列ごと捕まえ、動画の書き出し 1 回目の後に 約 84 MB が放置しても戻らなくなった（グループ 98 で発見）。リスナーを別の関数で作り、終わったら外すように直した（直した後は 60 秒放置で 117 MB に戻る）
- グループ 88 の判定（2 回目の後の増加 ≤ 30 MB）は変えていない。この一時的な保持を含むため **FAIL のまま**。参考として、書き出しのない時間が 45 秒続いた後の値を INFO に出す

### 7. グループ 98（診断）

- 削除せず、合否を判定しない診断として残した。通常の `npm run test:video`（グループ 80〜90）には含めず、`npm run test:video:diagnostic` でだけ実行する（`groups=98-98` を指定したときだけ動く）
- 内容: 3 分の動画の書き出し 4 回（mode=export）/ レンダリング中のキャンセル 3 回（mode=cancel）。各回の後に gc() → メモリ不足の通知 → プロセスの種類ごとのメモリ・JS ヒープを測定、60 秒放置の後・再生エンジンの破棄の後も測る
- 調査用のページの指定（試験用のページだけ）: `nohrtfkeeper=1`（HRTF のデータの保持を使わない。比較用）、`traceaudio=1`（ページ内の OfflineAudioContext のレンダリングの開始・完了を console.debug に出す）

- **Motion の CENTER の遅れ**: Motion ありの設定では、CENTER の音が距離の伝搬遅延（4〜4.4 m で 9〜10 ms）だけ映像より後ろに来る。意図した遅延（再生・Phase 06 と同じ）で、人が気づく同期ずれ（一般に ±20〜40 ms）より小さいが、0 ではない
- **WebM / MKV の「最後のフレームを延ばす」**: Matroska はフレームごとの長さを記録しないため、ファイル全体の長さで延ばす。Chrome / Edge の <video> では最後のフレームが表示され続けることを確認したが、映像トラックの終わりは 4.00 秒のまま。他のプレイヤー・編集ソフトでの扱いは未確認
- **複数の音声トラック**: 主な音声トラック（mediabunny の getPrimaryAudioTrack: コンテナの既定のトラック）だけを使い、出力の動画には加工した 1 トラックだけを入れる（他の音声トラック・字幕は入れない）
- **映像のコーデック**: 映像はコピーするので、入力のコーデックを出力のコンテナに入れられる組み合わせだけ書き出せる（例: MP4 → MP4）。HEVC はこの環境のブラウザでエンコードできず、試験の動画を作れなかったため未確認
- **プレビュー**: 入力の動画は canPlayType で、書き出したファイルは <video> / <audio> の読み込みエラーで、再生できない旨を表示する（ダウンロードはできる）。試験の環境では入力・出力とも再生できたため、この表示が出る場面は未確認
- **処理時間**: 3 分の動画で 1 回 47〜145 秒（大半は Phase 06 の音声のレンダリング、動画の書き込みは 2〜4 秒）。試験環境の負荷で大きく変わる
- 実際の動画ファイルでの確認・実楽曲・ヘッドホンでの試聴は未実施

### Motion の STFT の区切り（再生と書き出しのサンプル単位の差）

- 原因（Phase 06 の推定を確認）: 書き出しは STFT の区切りがメディアのサンプル 0, H, 2H… にあるが、実時間の再生はワークレットを作った時刻から数える。停止 → 再生のとき、入力が N + H サンプル以上無音なら状態を初期化して区切りをそろえるようにした
- 再生開始の通知（MessagePort）が音より先に届いた回だけそろう。そろった回は Motion ありでも各区間 −83〜−92 dB（Motion なしと同じ水準）、そろわない回は −37〜−44 dB（修正前と同じ）
- 再生を 30 ms 遅らせて通知を先に届ける方法は、曲の終わりの区間の差が −12〜−16 dB に悪化した（Motion なしでも。原因は特定できず）ため採用しなかった
- 今後の対策の候補: 再生開始の通知を音と同じ経路で伝える（AudioParam・入力チャンネルにメディアのサンプル位置を載せる）、または音より先に送ったことをワークレットから確認してから音源を始める
- 統計的な指標（周波数特性・ラウドネス・幅・相関・Motion の動き・余韻・ピーク）は以前から一致している（基準を満たす）

### 音響品質の測定（test:quality）

- 4 プリセットとも、サンプルピーク −1.00 dBFS・飽和 0・位相相関 ≥ 0（3 種の信号）。True Peak は −0.79〜−0.91 dBTP（サンプルピークのリミッターなので、天井をわずかに超える）
- HRTF を使う 3 つは 8〜10 kHz が −6〜−10 dB（ブラウザ内蔵の HRTF の癖。補正 EQ の後も残る。Phase SP の既知の制限）
- EDM 相当の信号で 4 プリセットとも −1.5〜−2.8 LU（基準 ±1 LU、FAIL）。Phase 08 でも同じ値（悪化ではない）。原因はリミッターの予算 3 dB（HALL + Motion の既知 FAIL と同じ種類の制約）。予算を上げる・ピークを潰すのは音質を変えるため行っていない
- 中央の声（L = R）: CINEMA 3D・IMMERSIVE X は ILD の揺れ 0.11 / 0.23 dB・位相相関 0.97 / 0.99 で中央に残る。360° MOTION は ILD 平均 +1.4 dB（CENTER LOCK 90% でもわずかに偏る）。LIVE ARENA は位相相関 −0.17（HALL の残響が左右で無相関のため。楽曲では正）→ 試聴の確認項目
- 動き: 50 ms ごとのレベルの最大の跳びは原音 +0.8 dB 以内（ステレオミックス）、2 階差分 / RMS は原音より小さく、クリックに当たる不連続は見つからない
- 余韻: 4 秒の無音の間、100 ms ごとのレベルが再び上がる量は最大 0.3 dB（自然に減衰）。LIVE ARENA の −60 dB まで 2.3〜2.6 秒

### 既知 FAIL の調査（変更なし・記録のみ）

- Motion 4 件・Tail 1 件: HALL + Motion のピーク対ラウドネス比（Phase 05 で特定）・CINEMA × Motion の ILD 変化幅（反射音の到達を正しくした結果）。直すにはリミッターの予算を上げるか、反射音・直接音のバランス（音色）を変える必要があり、試聴なしでは行わない
- DSP 1 件（EDM 相当の低域の絶対値）: 低域がすでに天井付近にある曲での物理的な制約（Phase 02.5）
